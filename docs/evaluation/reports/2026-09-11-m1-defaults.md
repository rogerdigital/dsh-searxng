# 2026-09-11 — M1 defaults validation (cold / warm-cache / burst)

Scope: latency and behavior validation of the M1 client-reliability defaults
(`cacheTtlMs 600000`, `minIntervalMs 1500`, token capacity 2, `queueCapacity 8`,
`totalBudgetMs 15000`) against a real managed instance, plus observed result-quality
behavior under battery repetition. This is **not** the task-quality baseline: no
answerability or usefulness judgments were made, and no search-quality claim follows from
this report.

## Pre-registered pass conditions

1. Burst (10 concurrent, default knobs): zero instance-side 429 errors, zero queue
   rejections (10 = burst 2 + queue 8 fits exactly), every query completes within the
   15 s budget.
2. Warm-cache: the immediate repeat of a query completes in under 10 ms.
3. Cold sequential with default pacing: each query pays at most ~1.5 s of pacing on top
   of its unpaced network time; no failures.
4. No unhandled errors in any scenario.

## Findings

1. **All four pass conditions held in both windows.** No 429s from the instance, no
   queue rejections at exactly 10 concurrent, burst tails (12.2–13.4 s) inside the 15 s
   budget, cache hits at 0–1 ms, no unhandled errors, and the burst staircase (two
   immediate, then ~1.5 s steps) matches the token bucket's design.
2. **Upstream engine cooldown under battery repetition (observed, window 2).** After
   ~30 queries in window 2 (on top of window 1 ~40 minutes earlier), the instance began
   returning HTTP-200 responses with **zero results** — from the last cold-pacing query
   onward, including every warm and burst query. Latency and HTTP health stayed normal.
   This is the known upstream-engine cooldown pattern (the lifecycle work already
   tolerates it in probes), now recorded as measured evidence: repeated identical-ish
   queries from one IP exhaust engine goodwill even with provider pacing active. It is
   exactly the failure surface `tune` (M2) is designed to make visible, and it bounds
   how quickly any evaluation battery may repeat queries.
3. **Cache stores empty success pages.** `warm-second` served the degraded empty result
   at 0 ms — an empty page is a success and is cached for the full TTL by design
   ("failures are never cached" covers errors, not empty pages). Follow-up design
   question recorded for M1.x/M2 kickoff: skip caching empty result sets so upstream
   recovery is not masked for 10 minutes.
4. **Pacing cost on sequential cold loops is real and bounded**: mean 911→1269 ms and
   840→1244 ms (+39–48%), at most ~1.5 s added per query after the first two. The
   designed trade for protecting upstream engines; repeats are absorbed by the cache.
5. **Watch item — burst tail approaches the budget.** The last queued query of a
   10-burst lands at ~12–13.4 s against a 15 s budget on this instance. A slower
   instance would push tail queries into honest budget/timeout failures; agents should
   treat pacing/budget `WEB_PROVIDER_ERROR`s as retryable.
6. **Expected-but-unmeasured edge**: an 11th concurrent query would reject as `busy`
   (queue capacity 8). Not exercised in this run; covered by unit tests.

## Decision

Keep the M1 defaults as shipped for this environment: the checklist item "Validate M1
defaults against cold and burst workloads before making them defaults" is satisfied for
latency and backpressure behavior on one host/network, with the limits above traveling
with the claim. Findings 2 and 3 are inputs to M2 (tune evidence rules) and to a small
M1.x decision (cache-empty behavior), not blockers. The full task-quality baseline
(answerability per `tasks-v1.md`) remains open and is the next evaluation work; it must
space repetitions to respect the observed cooldown.

## Reproduction

Runner (session-level, exercised the packaged provider from the locally built `lib/`):

```mjs
import { performance } from 'node:perf_hooks'
import { SearxngSearchProvider } from '<repo>/lib/index.mjs'

const BASE = 'http://127.0.0.1:8080'
const QUERIES = [/* first ten tasks of docs/evaluation/tasks-v1.md, in order */]

const newProvider = (overrides = {}) =>
  new SearxngSearchProvider({ baseURL: BASE, ...overrides })

async function timedSearch(provider, query, label) {
  const startedAt = performance.now()
  try {
    const result = await provider.search({ query })
    return { label, query, ms: Math.round(performance.now() - startedAt), sources: result.sources.length, error: null }
  } catch (error) {
    return { label, query, ms: Math.round(performance.now() - startedAt), sources: 0, error: String(error?.message ?? error) }
  }
}

// cold-unpaced: sequential, 300 ms gap, { cacheTtlMs: 0, minIntervalMs: 0 }
// cold-default-pacing: sequential, { cacheTtlMs: 0 }
// warm: default knobs, identical query twice back to back
// burst: Promise.all over ten distinct queries, default knobs
```

Environment preparation: `pnpm build && node lib/cli.mjs setup --profile web --port 8080`,
then `node lib/cli.mjs status --profile web --json` (all checks must pass) before timing.
